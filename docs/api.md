# API Reference

Base URL: `http://127.0.0.1:3000/api`. All responses are JSON. Errors are
`{ "error": "<message>" }` with a `4xx`/`5xx` status — Arabic messages for
user-facing validation errors (e.g. "المورد غير موجود"), plain
`err.message` for unexpected server errors. No auth — single-user offline
desktop app.

Route files live in `src/routes/`, mounted in `src/app.js`. This list is
generated from the actual route definitions (verified by reading every file
directly, not reconstructed from memory) — if it ever disagrees with the
code, the code wins; fix this file.

|---|---|---|
| GET | `/search?query=` | Name + alias search (Arabic-normalized), limit 10 |
| GET | `/:id/price-history` | Points (date/price/qty/supplier/invoiceNumber) + stats (min/max/avg/first/last/change/trend) |
| POST | `/` | Body: `{ name, barcode, category, unit }` |

## Suppliers — `/api/suppliers`

| Method | Path | Notes |
|---|---|---|
| GET | `/?query=` | List, or search if `query` present |
| GET | `/aging` | Debt aging report — **registered before `/:id`** |
| GET | `/:id` | 404 if not found |
| GET | `/:id/ledger` | Raw `supplier_transactions` rows |
| GET | `/:id/statement?startDate=&endDate=` | Date-filterable statement |

| POST | `/:id/adjust` | Body: `{ amount, reason }`. Manual balance adjustment, amount ≠ 0 |

## Purchase Orders — `/api/purchase-orders`

| Method | Path | Notes |
|---|---|---|
| GET | `/` | List all, with item-count aggregate (single-child-table join, safe — see `database.md`) |
| GET | `/:id` | Header + items, 404 if not found |

## Invoices (purchasing, OCR pipeline) — `/api/invoices`

Two-state workflow — see `business-rules.md` and `import-flow.md` for the
full "why". Every OCR import lands at `Pending Review`; every item-editing
route below is rejected once the invoice is `Approved`.

| Method | Path | Notes |
|---|---|---|
| POST | `/ocr` | Body: raw OCR JSON payload. Always creates the invoice as `Pending Review` — no auto-approve. Runs `invoiceProcessor.processOcrResult()` — see `import-flow.md` |
| GET | `/pending` | Invoices awaiting review |
| GET | `/approved?limit=20&offset=0` | Paginated |
| GET | `/:id/review` | Invoice header (incl. `approved_at`, set only once, at approval) + line items (with match candidates). Backs both the Pending-Review edit UI and the Approved read-only view page — same endpoint, works for either status |
| PATCH | `/:id/items/:itemId` | Body: `{ productName?, quantity?, unit?, unitPrice?, productId?, createNewProduct?: {unit} }`. Corrects fields and/or resolves the product match. **Pending Review only** |
| POST | `/:id/items` | Body: `{ productName, quantity, unit?, unitPrice, productId?, createNewProduct?: {unit} }`. Adds a missing line. **Pending Review only** |
| DELETE | `/:id/items/:itemId` | Removes an incorrect line; rejected if it's the last one. **Pending Review only** |
| POST | `/:id/approve` | No body. Requires every item to already have `product_id` set — 400 naming the unmatched items otherwise. Locks the invoice and posts stock/debt/cost/accounting |
| PATCH | `/:id/notes` | Body: `{ notes }`. The one field still editable after approval |

Frontend routes over this same `GET /:id/review` data: `desktop`'s
`/invoices/:id/review` is the editable Pending-Review screen;
`/invoices/:id` is the dedicated read-only view page for an Approved
invoice (`InvoiceViewPage.tsx`) — it redirects to `/review` if the invoice
somehow isn't actually Approved yet.

## Payments (cross-supplier view) — `/api/payments`

| Method | Path | Notes |
|---|---|---|
| GET | `/` | Every payment ever recorded against any supplier, newest first — a flat ledger view, not a domain of its own (payments are actually written via `POST /api/suppliers/:id/payments`) |

## Reports (accounting-side) — served by `/api/accounting`

No separate `/api/reports` route file — the Reports frontend module calls
`accounting`'s `trial-balance`/`balance-sheet`/`profit-loss`/`verify`
endpoints directly.

## Customers (wholesale, sales domain) — `/api/customers`

Independent of everything above — see `business-rules.md` for the hard
boundary (no stock/accounting/supplier interaction).

| Method | Path | Notes |
|---|---|---|
| GET | `/?query=` | List with computed `current_balance` (correlated subqueries, never a JOIN — see `database.md`) |
| POST | `/` | Body: `{ fullName, phone, address, notes }` |
| GET | `/reports/summary` | Totals, largest debtors, most active, avg invoice value — **registered before `/:id`** |
| GET | `/:id` | 404 if not found |
| GET | `/:id/invoices` | List for one customer |
| POST | `/:id/invoices` | Body: `{ invoiceDate, items, notes }`. Transaction: sums items → reads current computed balance → inserts invoice with frozen `previous_balance`/`new_balance` → generates `SINV-NNNNNN` number → inserts items |
| GET | `/:id/invoices/:invoiceId` | Header + items, 404 if not found |
| GET | `/:id/payments` | List for one customer |
| POST | `/:id/payments` | Body: `{ paymentDate, amount, paymentMethod, notes }`. Plain insert — no invoice linkage, no overpayment guard (deliberate, see `business-rules.md`) |
| GET | `/:id/statement` | Window-function running ledger — see `database.md` |

## Adding an endpoint — checklist

1. Business logic goes in the matching `services/*.js` file (new service if
   it's a new domain) — never write query logic or validation directly in
   the route handler.
2. Route handler stays thin: parse `req.params`/`req.query`/`req.body`, call
   the service, `res.json(...)`, `try/catch` → `res.status(...).json({error})`.
3. If it's a single-segment literal route on a resource that already has a
   `/:id` route, register it **before** `/:id` (see `architecture.md`
   route-ordering rule).
4. Mount new route files in `src/app.js` if it's a new resource.
5. Update this file and, if the endpoint touches a new table or business
   rule, `database.md`/`business-rules.md` too.
