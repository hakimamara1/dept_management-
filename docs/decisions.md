# Architecture Decision Records

Format: **Decision / Reason / Consequences / Status**. Newest last. Add a
new ADR here *while* making a non-obvious implementation choice, not after —
per the standing documentation rule in `project-summary.md`.

---

### ADR-001: Electron + HTTP sidecar, not Electron IPC

**Decision**: Electron's main process only opens a `BrowserWindow` and
spawns the existing Express backend as a local child process
(`desktop/electron/main/backend-process.ts`), polling `/health` until ready.
The renderer talks to the backend over plain HTTP to `127.0.0.1:3000`,
exactly like a web app. There is no `ipcMain`/`ipcRenderer`/`contextBridge`
data path anywhere.

**Reason**: The backend (Express + better-sqlite3, five-layer
routes→services→queries→statements→schema) already existed and worked
before the Electron rewrite. Rewriting all business logic into Electron
main-process IPC handlers would mean re-deriving every route as an IPC
channel for no functional gain — HTTP already does everything IPC would,
with less new code and less risk during the rewrite.

**Consequences**: Packaging requires the backend to be spawn-able inside a
packaged app (`ELECTRON_RUN_AS_NODE`, native module rebuild — see
`roadmap.md`). If this were ever a networked multi-machine app instead of a
single offline desktop app, HTTP was already the right shape.

**Status**: Accepted, implemented, unchanged across every module built since.

### ADR-002: Hand-written shadcn/ui primitives, not the shadcn CLI

**Decision**: Every `desktop/src/shared/components/ui/*` primitive
(button, dialog, select, etc.) is hand-written source, copied/adapted from
the shadcn/ui pattern, rather than generated by `npx shadcn@latest add ...`
or any scaffold CLI.

**Reason**: `npm create`/`npx <scaffold-cli>` commands are blocked by this
environment's auto-mode security classifier as "agent-guessed external
codegen" unless the user names the exact package explicitly. Rather than
stall the whole frontend rewrite on that, every primitive was hand-written
directly as owned source files.

**Consequences**: These files are not a vendored dependency — they can and
should be edited directly when a component needs to change, with no "don't
touch generated code" concern. No `components.json`/shadcn config exists in
the repo, which is expected and correct.

**Status**: Accepted, implemented.

### ADR-003: `HashRouter`, not `BrowserRouter`

**Decision**: `app/router.tsx` uses React Router's `HashRouter`.

**Reason**: A packaged Electron renderer loads from a `file://` path with
no server behind it. `BrowserRouter` depends on the History API resolving
real paths against a server (or a SPA-fallback rewrite rule) — neither
exists for a `file://` load, so deep links and refreshes would break.
`HashRouter` keeps all routing client-side via the URL fragment, which needs
nothing from the environment.

**Consequences**: URLs look like `#/customers/3` instead of `/customers/3`.
Irrelevant for a desktop app with no shareable web URLs.

**Status**: Accepted, implemented.

### ADR-004: No ORM — centralized raw SQL + `better-sqlite3`

**Decision**: All SQL lives as string constants in `src/models/queries.js`,
namespaced by domain, prepared once at startup into `db.stmts.<namespace>`.
No Repository classes, no DTOs, no ORM (Prisma/Sequelize/etc.).

**Reason**: The app's size and single-developer-velocity needs don't justify
an ORM's abstraction cost. Centralizing every query string in one file makes
the entire SQL surface auditable in one place — which is how the `HAVING`-
alias bug (see `database.md`) was found and fixed quickly: a single grep
across `queries.js` was enough to confirm it was the only instance.

**Consequences**: Every new query must be added to `queries.js` and
registered in `config/database.js` — there's no "just write `db.query(...)`
inline" escape hatch (one historical exception, `stockService`'s dead
`QUERIES.products.getLowStock` reference, was itself a bug — fixed by
switching to the centralized `db.stmts.stock.getLowStock`).

**Status**: Accepted, implemented, held through every module.

### ADR-005: Correlated subqueries over JOIN+GROUP BY for multi-child aggregates

**Decision**: Any query aggregating two different child tables of the same
parent (e.g. a customer's invoice totals *and* payment totals) uses
correlated scalar subqueries, one per aggregate — never a single
multi-table `JOIN ... GROUP BY`.

**Reason**: Joining two child tables before aggregating causes row fan-out
(3 invoices × 2 payments = 6 joined rows), which silently multiplies `SUM()`
results. This is a real, easy-to-write bug class, not a hypothetical —
caught during design of the Customers module before it ever shipped.

**Consequences**: Slightly more verbose SQL than a single join. Correct in
all cases. `purchaseOrders.getAll` deliberately does use a join because it
only aggregates *one* child table (`purchase_order_items`) — fan-out can't
happen with a single child table, so the simpler form is safe there.

**Status**: Accepted, implemented in `customers.*` queries.

### ADR-006: Customer balance is never a stored column

**Decision**: `customers` has no `balance`/`current_balance` column. Every
read computes `SUM(sales_invoices.invoice_amount) − SUM(customer_payments.amount)`
on the fly.

**Reason**: Explicit requirement from the Customers-module spec, to avoid a
maintained value drifting from its ledger. This deliberately differs from
`suppliers.current_balance`, which *is* a maintained snapshot column — both
are intentional, not an inconsistency.

**Consequences**: Every list/detail view for customers needs a correlated-
subquery aggregate (ADR-005) instead of a cheap column read. Given this
app's data volumes (single-business wholesale ledger, not a high-throughput
system), the read cost is negligible.

**Status**: Accepted, implemented.

### ADR-007: Sales invoice line items are free text, not FK'd to `products`

**Decision**: `sales_invoice_items.product_name` is a plain `TEXT` column
with no foreign key to the `products` catalog.

**Reason**: The Customers-module spec explicitly forbids this module from
touching inventory/stock. If sales invoice items referenced `products`, it
would create pressure to eventually decrement stock on a sale — which is
out of scope by design. Free text keeps the coupling impossible, not just
discouraged.

**Consequences**: No autocomplete against the existing product catalog when
building a sales invoice (unlike Purchase Orders, which do use
`ProductPicker` against the real catalog) — the sales invoice form uses a
plain text `Input` for each line's product name. If the business later
wants stock-linked sales, that's a new, explicit decision — not a natural
extension of this schema.

**Status**: Accepted, implemented.

### ADR-008: Customer payments are never allocated to a specific invoice

**Decision**: `customer_payments` has no `invoice_id` column. A payment
reduces the customer's overall account balance; there is no "this payment
paid off invoice #4" relationship anywhere in the schema or UI.

**Reason**: Explicit requirement from the spec — wholesale customers pay
against their account, not per-invoice, mirroring how the supplier side
already works (`supplier_transactions` also has no invoice-specific
allocation for payments).

**Consequences**: The Account Statement (running ledger) is the only way to
see chronological invoice/payment history; there's no "outstanding invoices"
view that shows which specific invoice is unpaid. This is accepted as
correct given the account-level payment model, not a missing feature.

**Status**: Accepted, implemented.

### ADR-009: Invoice `previous_balance`/`new_balance` are frozen historical facts

**Decision**: Both `purchase_invoices` and `sales_invoices` store
`previous_balance`/`new_balance` computed once at creation time, never
recalculated afterward — even though the "no stored balance" rule (ADR-006)
otherwise applies to the live account balance.

**Reason**: These aren't a duplicate of the live balance — they're a
snapshot of what the balance *was* at the moment a specific document was
issued, which is what gets printed on the invoice. A printed invoice's
footer must not silently change if later payments happen. This is the same
pattern the purchasing side already used for `purchase_invoices`, applied
consistently to `sales_invoices`.

**Consequences**: If a customer's balance is later corrected/adjusted, past
invoices keep showing the balance as it was when issued — this is the
desired behavior for an immutable financial document, not a bug.

**Status**: Accepted, implemented.

### ADR-010: PO price-field default from last purchase cost (UX only, not a data rule)

**Decision**: When adding a product line to a new Purchase Order, the unit-
price field pre-fills from that product's `last_purchase_price` (fallback
`average_cost`), but only if the field is currently empty — the user can
freely overwrite it before submitting.

**Reason**: Direct user request — most POs re-order at roughly the last
known cost, so pre-filling saves re-typing while staying fully editable.

**Consequences**: This is UI convenience only; nothing in the backend
enforces or assumes the PO price matches `last_purchase_price`. A PO's
stored price is whatever the user submitted, full stop.

**Status**: Accepted, implemented in `CreatePOSheet.tsx`.

### ADR-011: Bug fix — `stock.getLowStock` `HAVING` clause resolved against the wrong column

**Decision**: Rewrote `HAVING current_stock < ?` to
`HAVING COALESCE(SUM(sm.quantity), 0) < ?` in `queries.js`.

**Reason**: SQLite resolves a bare identifier in `HAVING` against a real
table column in scope *before* a SELECT-list alias of the same name.
`products.current_stock` is a real (always-stale) column, so the alias
`current_stock` in the low-stock query was silently comparing against that
stale column instead of the computed `SUM()`, returning every product
regardless of the threshold. Full writeup in `database.md`.

**Consequences**: Fixed the Dashboard's "needs attention" low-stock panel,
which had been silently broken (showing all products, not just low-stock
ones). This is the only `HAVING` clause in the codebase (verified by grep)
— any future one must repeat the aggregate expression rather than reuse an
alias that collides with a real column name.

**Status**: Fixed and verified via isolated repro + live endpoint check.

### ADR-012: Bug fix — `productMatcher.confirmMatch` no longer cross-invoice `UPDATE`s

**Decision**: `confirmMatch(ocrName, productId)` now only inserts/updates a
`product_aliases` row. It no longer runs
`UPDATE purchase_invoice_items SET product_id = ? WHERE normalized_ocr_name = ?`.

**Reason**: That `UPDATE` was unscoped to the current invoice — it matched
*every* historical item across *any* invoice that happened to share the
same normalized OCR text, silently repointing unrelated past invoices'
product links whenever a human resolved a match on an unrelated current
invoice. The caller (`approveInvoice` in `invoiceProcessor.js`) already
updates the current item correctly, scoped by its own `itemId`
(`db.stmts.updateItemProduct.run(productId, 'UserSelected', itemId)`) — the
alias write was the only thing `confirmMatch` needed to do.

**Consequences**: Historical invoice data integrity is preserved. Future
product-matching confirmations only affect the alias table (used for
*future* OCR matches) and the one item explicitly being resolved.

**Status**: Fixed and verified.

### ADR-013: File-based `docs/` as the persistent source of truth

**Decision**: Established `docs/architecture.md`, `database.md`,
`business-rules.md`, `api.md`, `import-flow.md`, `reporting.md`,
`roadmap.md`, `decisions.md`, `changelog.md`, `project-summary.md` as a
standing, always-updated documentation system, verified against the actual
code rather than reconstructed from memory/chat history.

**Reason**: Direct user request, framed as a standing instruction: any
future session (with no access to this conversation) must be able to read
`docs/` and continue the project correctly, and every future architectural/
business/implementation decision must be recorded here as it's made, not
after the fact.

**Consequences**: Every completed feature going forward must update the
relevant doc file(s) in the same turn, and any new non-obvious
implementation choice gets a new ADR here before or while the code is
written — not as a follow-up task.

**Status**: Accepted, in effect for all future work in this project.
